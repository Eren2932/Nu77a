# Архитектура

## Общая картина

```
┌──────────────────────┐         HTTPS / WSS        ┌────────────────────┐
│   Android (Kotlin)   │ ─────────────────────────► │  Caddy (TLS, авто) │
│   Compose UI         │                            └─────────┬──────────┘
│   Ktor + WebSocket   │                                      │ HTTP
│   EncryptedPrefs     │                            ┌─────────▼──────────┐
└──────────────────────┘                            │  nuva-server (Go)  │
                                                    │  chi + ws.Hub      │
┌──────────────────────┐                            └─────┬────────┬─────┘
│   Web (React, 1.1)   │ ─────────────────────────►       │        │
└──────────────────────┘                          ┌───────▼──┐  ┌──▼──────┐
                                                  │ Postgres │  │ media   │
                                                  └──────────┘  │ (диск/S3)│
                                                                └─────────┘
```

Один процесс, одна база, один прокси. Всё поднимается `docker compose up -d`.
Ничего лишнего не добавляем, пока текущее не начнёт упираться.

## Сервер

```
server/
├── cmd/nuva-server/main.go   загрузка конфига, миграции, graceful shutdown
└── internal/
    ├── config/     ЕДИНСТВЕННОЕ место, где читается os.Getenv
    ├── store/      Postgres: пул, миграции, репозитории
    ├── auth/       bcrypt, JWT, refresh-токены, recovery-коды
    ├── api/        роутер, middleware, HTTP-хендлеры
    └── ws/         realtime-хаб и envelope-протокол
```

Правила, которые держат это в порядке:

* **Направление зависимостей только вниз.** `api` знает про `store` и `auth`;
  `store` не знает про `api` никогда.
* **Никаких глобальных переменных.** Всё передаётся через конструкторы —
  поэтому любой слой тестируется отдельно.
* **`config.Load()` падает на старте**, если нет обязательной переменной.
  Забытая переменная становится ошибкой запуска, а не загадочной 500-й в бою.
* **Миграции применяются автоматически при старте**, каждая в своей транзакции.
  Разъехаться прод и локалка физически не могут.

### Схема БД

Все таблицы для 1.0 созданы уже сейчас (`0001_init.sql`): `users`, `sessions`,
`conversations`, `conversation_members`, `messages`. Контракт клиента не будет
дёргаться в середине разработки.

Ключевые решения:

* `messages.seq` — монотонный номер **внутри диалога**. Клиент синхронизируется
  как «дай всё после seq N», без сравнения времени на разных устройствах.
* `UNIQUE (conversation_id, sender_id, client_id)` — идемпотентность отправки.
  Повторная отправка при обрыве сети не создаёт дубликат сообщения.
* `conversation_members.last_read_seq` — статус «прочитано» одним числом, а не
  таблицей на каждое прочтение.

### Аутентификация

```
пароль ──bcrypt(cost 12)──► users.password_hash

вход ──► access token (JWT, 15 минут, HS256, привязан к session id)
     └─► refresh token (32 случайных байта, 60 дней)
             └─► в БД только SHA-256 хеш
```

* Утечка базы **не даёт** живых сессий: там только хеши.
* Refresh-токен **одноразовый**: при обновлении он ротируется, старый мгновенно
  мёртв. Кража токена обнаруживается сама.
* Access-токен несёт `sid`, поэтому конкретное устройство можно отключить.
* Recovery-код показывается ровно один раз при регистрации. Сервер хранит
  только bcrypt-хеш и восстановить код не может — это не баг, это смысл.

### Realtime

Один формат кадра в обе стороны:

```json
{ "type": "send_text", "id": "client-generated", "payload": { } }
```

`ws.Hub` держит `map[userID] -> set[*Client]`. У каждого клиента буфер на 64
сообщения; если телефон не успевает — соединение закрывается, и он
досинхронизируется по HTTP при переподключении. Одно застрявшее устройство не
может затормозить сервер.

Когда понадобится второй инстанс: `Hub.SendToUser` начнёт публиковать в Redis,
всё остальное не изменится.

## Android

```
club.nuva.app/
├── data/
│   ├── local/SessionStore       токены в EncryptedSharedPreferences
│   ├── remote/NuvaApi           единственное место, где живёт HTTP
│   ├── remote/RealtimeClient    WebSocket + backoff с джиттером
│   └── repository/              бизнес-логика поверх api + local
├── di/ServiceLocator            6 синглтонов вручную, без Hilt
└── ui/                          Compose-экраны + ViewModel
```

* **Однонаправленный поток данных.** ViewModel отдаёт `StateFlow<UiState>`,
  экран его отображает. Никакого состояния внутри Compose-функций.
* **Навигация от факта, а не от стека.** Есть сессия → чаты, нет → вход.
  Невозможно оказаться в «наполовину вышел».
* **Обновление токена невидимо для UI.** Ktor Auth сам обновляет пару токенов
  на 401 и повторяет запрос. Экраны про это не знают.
* **Реконнект с джиттером.** Без случайной добавки все телефоны мира
  переподключаются в одну секунду после рестарта сервера и роняют его снова.
* **Без Hilt осознанно.** Минус один кодогенератор — минус целый класс ошибок
  сборки. При росте графа выше ~15 объектов заменим один файл.

## Контракт клиент ↔ сервер

`server/internal/api/handlers_*.go` ↔ `data/remote/Dto.kt` — зеркало.
Меняешь поле — меняешь обе стороны в одном коммите.

Страховка на случай рассинхрона: клиент декодирует JSON с
`ignoreUnknownKeys = true`, поэтому новое поле на сервере не ломает старые
установленные APK.

## Что сознательно НЕ сделано в спринте 0

Чтобы не строить абстракции под будущее, которого может не быть:

* нет кеша сообщений в SQLite (спринт 2, вместе с самими сообщениями);
* нет Redis (не нужен до второго инстанса);
* нет gRPC/protobuf (JSON читается глазами, отлаживается curl-ом);
* нет очереди задач (нечего в неё класть);
* нет E2EE (спринт после 1.0, см. SECURITY.md — обещать раньше нельзя).
